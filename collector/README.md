# 菜单统计

## 记哪些事件

**第 0 期 · 会话层**

| 事件 | 什么时候发 | 带什么 |
|---|---|---|
| `open` | 菜单渲染完 | 初始语言（`es` / `en` / `zh`） |
| `lang` | 客人点了语言按钮 | 切到哪个语言 |
| `staff` | 客人点了「给服务员看」 | —（按钮在「清单」那张卡里，没建清单的人看不到） |

**第 1 期 · 菜品层**

| 事件 | 什么时候发 | 带什么 |
|---|---|---|
| `imp` | 卡片露出一半**并停留 1 秒** | 菜号 + 来源 |
| `det` | 点开菜品详情 | 菜号 + 来源 |
| `add` | 加进清单（含套餐、推荐搭配带进去的） | 菜号 + 来源 |
| `pair` | 走的是详情页「推荐搭配」那个按钮 | 菜号 |
| `combo` | 加了多人套餐 | 套餐 id |
| `drink` | 加了饮料 | 饮料 id + 来源 |

`imp` 的口径是有意卡严的：划过去不算。三层用的是同一批会话，相除才有意义——
「看到的人里有多少点开」「看到的人里有多少加进清单」。
按次数算的话，同一个人反复点同一道菜就会把分子撑大。

### 第 1.5 期：来源（2026-11-07 加的）

同一道菜，从节气推荐点进清单和从菜单正文点进清单，**含义完全不一样**：
前者说明「推荐有效」，后者说明「菜本身有吸引力」。之前只记菜号，这两件事混成一笔。

`imp` / `det` / `add` / `drink` 都带一个 `src`：

| `src` | 哪儿 | 会记 `imp` 吗 |
|---|---|---|
| `menu` | 菜单正文的菜品卡片 | 会 |
| `luck` | 节气随机推荐 | 会 |
| `first` | 顶层「第一次来点什么」 | 会 |
| `hero` | 首屏那个 1-1 的加按钮 | 不会（没有卡片） |
| `det` | 详情页里（含推荐搭配那一行主食） | 不会 |
| `pairbox` | 详情页「整套加入」带进去的一批 | 不会 |
| `order` | 清单里结算前的加点（`UPSELL` 那些高毛利小菜） | 不会 |
| `pick` | 「其他小菜 / 其他饮料」全屏列表 | 不会 |
| `pack` | 多人套餐带进去的 | 不会 |
| `drinks` | 酒水单 | 不会 |

只有前三处有曝光可言，所以只有它们能算「看到→加入」的转化率，其余是点出来的，没有分母。

`imp` 的去重键是「菜 + 来源」，不是光菜号：一道菜在节气框和菜单正文各算一次露出，
因为两边的分母要各自跟自己那边的 `add` 对上。只按菜号去重的话，
从节气框加的菜会被算进菜单正文的转化率里，归因就错了。

加新区域要三处同步，少一处就会落成空来源：
`source/app.js.tpl` 的 `SRC`、`collector/worker.js` 的 `SRCS`、`collector/_names.py` 的 `SRCN`。
（`SRCN` 和菜名的对照表 2026-11-08 从 `_report.py` 挪进了 `_names.py`，报表和看板共用一份。）
`SRC` 的顺序有讲究——`#bebidas` 嵌在 `#menu` 里，必须排在 `menu` 前面。

2026-11-07 之前收的行 `src` 是 `NULL`，报表归到「(旧)」一档。

`staff` 是目前最接近「成单」的信号。它不等于成单：客人可能看完改主意，服务员也可能录成别的。
真实销量在店里那套 POS 里，这边拿不到。同理，`add` 是「进了清单」，不是「卖出去了」。

**`staff` 的分母是「建了清单的会话」，不是全部会话。** 按钮 `#ostaff` 渲染在清单那张卡
（`renderOrder` 的 `.oact`）里，没建清单根本看不到它——32 个点过的会话里 31 个也有 `add`，
剩下那 1 个是回头客，清单存在 localStorage 里，所以这次没 `add` 也能打开。
拿全部会话当分母的话，建清单率一掉它就跟着掉，看着像按钮出了问题。

## 收了什么、没收什么

**收：** 会话 id（随机生成，只存在那台手机的内存里，页面一关就没了）、事件名、初始语言、屏幕宽度（按 60px 分桶）、国家代码、服务端收到的时间。

**不收：** IP（Worker 能看到，代码里明确不写入库）、精确位置、User-Agent、任何自由文本、任何能认出是谁的东西。

**不写 cookie，也不写 localStorage。** 所以不需要 cookie 横幅。菜单本身用 localStorage 存客人的清单和语言偏好，那是客人主动要求的功能，和统计是两回事，统计这部分一个字节都不往设备上写。

浏览器开了 Do Not Track 或 Global Privacy Control 的，直接不上报。

**保留期：** 原始事件留 90 天。Worker 每天 04:17 UTC 跑一次定时任务自动删掉过期的，
代码在 `worker.js` 的 `scheduled()` 里，天数是 `KEEP_DAYS`。按天聚合的长期趋势留给第 2 期的报表页。

## 看数据

### 看板（平时看这个）

**看板就是一个网址**，手机上存成书签，打开就是当下的数字——不用电脑，不用命令行：

```
https://sibisi-stats.cartaviva.workers.dev/d?k=<DASH_TOKEN>
```

页面上那排按钮是**头部那组卡片覆盖几天**：`今天` / `最近 3 天` / `最近 7 天` /
`最近 30 天`（网址上是 `&r=1|3|7|30`）。卡片和基线都跟着它走：

- `今天` = 最后一天，按今天**实际开过的档口**取基线（只开了午市就只拿前几天的
  午市比，不然是拿半天比整天）
- `最近 N 天` = 最后 N 个**营业日**，整天对整天，基线是再往前 N 个营业日。
  营业日 = 会话 ≥5 的日子：周四休息、和今天早上那种还没开门的半天都不算一天。
  数据不够 N 天时照样出数，但会多一条「其实只有 X 个营业日」的结论
- 计数型指标（扫码会话、桌面宽度会话）一律摊成**每天**，不然选 3 天看着像翻三倍

**这里没有缓存**，每次打开都现算——所以「刷新页面就是最新的数字」这句话是真的。
右上角那个 `↻ 刷新` 只是一个带时间戳的链接，点了必定走一次新请求。
试过两种缓存都不行：Cache API 在 workers.dev 上不生效；模块级变量也靠不住，
Cloudflare 常常给每个请求一个新 isolate，实测几乎次次 miss。代价是每次打开查一次
D1（现在一次几千行，离每天 500 万行的免费额度很远）；真到了那一步，正经做法是在
D1 里开张 cache 表。

页面顶上写着是几点算的。

`DASH_TOKEN` 是看板**专用**的口令，和脚本用的 `TOKEN` 分开——它要进手机的浏览器
历史，想换就换，不影响电脑上那些脚本。两个口令都只能读，读到的也只有聚合数字，
没有 IP、没有任何能认出客人的东西。没设 `DASH_TOKEN` 的话 `/d` 也认 `TOKEN`。

懒得找书签的话：

```bash
~/git/sibisi/collector/dash.sh        # 从钥匙串取口令，直接开浏览器
~/git/sibisi/collector/dash.sh 30     # 拉 30 天的数据
~/git/sibisi/collector/dash.sh 14 s   # 不开浏览器，存一份到 out/（离线留档）
```

存下来那份走的是 `&bare=1`：页面里不放换窗口的链接，所以**口令不会写进 HTML**。

`out/` 不进 git。

## 看板是怎么搭的

`dash.js` 分三层，改东西只动对应那一层。它跟着 `worker.js` 一起部署，
所以**改完要 `npx wrangler deploy`** 才生效。

| 层 | 在哪 | 干什么 |
|---|---|---|
| 聚合 | `Ses` / `Bucket` / `Ctx` | 把会话按「业务日 × 午市/晚市」归堆，只做计数，不下结论 |
| 公式 | `metric(...)` 注册的函数 | 一个指标一个函数：输入一个 Bucket，输出一个数 |
| 结论 | `rule(...)` 注册的函数 | 一条结论一个函数：输入整段数据，输出一句话或者 `null` |

`worker.js` 只负责把事实从 D1 搬出来（`raw_counts`，一条 SQL），一点分析都不做。
聚合写进 SQL 就等于把公式焊死在服务端，改一个口径要动数据库那一层。

**加一个指标**：在公式层写个函数就行，卡片、走势图、和基线的对比全自动跟着出来。

```js
metric("pair_rate", "用了推荐搭配",
  { unit: "%", note: "详情页那个「整套加入」" },
  (b) => F(b.sv("pair"), b.sv("det")));
```

页面最后那段「这些数是怎么算的」是拿 `fn.toString()` 把箭头右边那截直接印出来的，
所以**公式不会和算的不一样**——别把它另抄一份。

**加一条结论**：在结论层写个函数，阈值写死在函数里。满足条件它才出现。

**改之前先在本地跑一遍**，不用部署：

```bash
cd collector
T=$(security find-generic-password -a sibisi-stats -s sibisi-stats-token -w)
curl -sS "https://sibisi-stats.cartaviva.workers.dev/r?k=$T&d=14" > /tmp/raw.json; unset T
node --input-type=module -e 'import fs from "node:fs";
  const m = await import("./dash.js");
  fs.writeFileSync("/tmp/d.html", m.dashboard(JSON.parse(fs.readFileSync("/tmp/raw.json","utf8")), {days:14}));'
open /tmp/d.html
```

几个口径上的讲究，别绕过去：

- 比率一律返回 `F(分子, 分母)`，不直接返回百分数。分母带着走，引擎才能在
  分母太小的时候直接不出数——否则 1/1 会变成一条「100%」的假结论挂在页面上。
  门槛是每个指标自己的 `min_b`。
- **计数型指标**（会话数这种）要写 `per_day: true`，当基线用的时候除以天数，
  不然等于拿一天去比一整周。
- **基线按今天实际有的档口取**。今天只开过午市就只拿前几天的午市比，
  不然周日下午看板会显示「比昨天少一半」——其实只是晚市还没开。
- 会话数少于 5 的日子（周四休息、或者只有自己在测）不算进基线。
- 「清单里几道菜」按**不同的菜**算，不按加入次数：真有会话把同一道菜连点了 20 下，
  按次数算它一个人就能把全店平均值翻倍。页面上有条结论专门盯这种会话。

## 免费额度够不够

Workers 每天 10 万请求，D1 每天 10 万行写入、5 GB 存储。

按每天 60 桌扫码、第 1 期全开估算：一个会话从头翻到尾大约 40 个事件
（35 道菜的曝光 + 点开和加入），批量发送后约 1–2 个请求。

| | 每天用掉 | 免费额度 | 占比 |
|---|---|---|---|
| Workers 请求 | ~120 | 100,000 | 0.1% |
| D1 写入行数 | ~2,400 | 100,000 | 2.4% |
| D1 存储 | 90 天累计约 17 MB | 5 GB | 0.3% |

生意翻十倍也还在免费额度内。真要逼近上限，先调 `app.js.tpl` 里 `dishSpy` 的停留门槛
（现在 1 秒），把「划过去」滤得更狠。

## 已知的坑

### 一种饮料两套 id

推荐加点 / 推荐搭配 / 多人套餐发的 `drink` 事件，值是 `DRK` 的短键（`ts`）；
酒水单和「其他饮料」那个全屏列表发的是 `DR` 的 id（`dr-beers-3`）。两个指的是
同一款青岛，但在榜上会排成两行，看着像两种酒——2026-11-09 就是这么被发现的
（青岛 9 次 + 青岛啤酒 3 次；可乐那边更隐蔽，`ccz` 和 `dr-soft-0` 差着 7 次）。

归并表是 `data.py` 里本来就有的 `DRKMAP`，以酒水单那套 id 为准，经 `_names.py`
的 `DRCANON` 导给看板（`canonDrink()`）和终端报表（`canon_drink()`）。
**事件照旧发原来的值**——客人点的是「可口可乐」还是「零度」是真实信息，
只是酒水单把它们印成一行，所以只在显示时合并。

一个残留：终端报表那栏加的是**会话数**，同一个会话从两处各点一次同一款酒会被数
两次（看板按次数算，归并是准的）。数字小的时候无所谓。


**`ts` 是「上报时间」，不是「发生时间」，所以现在做不了时段分析。**
事件先攒在 `EVQ` 里，只在两种时候发出去：攒到 40 条，或者页面被切后台 / 关掉
（`app.js.tpl` 的 `evFlush`，没有定时上报）。一个会话的 40 条事件会带着**同一个**
毫秒数落库，所以「每 15 分钟几个人」画出来的是「几个人在这一刻放下手机」。
2026-11-07 晚上 22:00 那一格看着有 10 个会话扎堆，其实是 9 个会话的 40 条缓冲
同时满了——不是来了一波客人。
要真做时段分析，得给每条事件带一个客户端相对偏移，或者让 `open` 立即单独发一次。
**同一会话内事件的先后顺序是可靠的**（按数组顺序入库），只有绝对时刻不可靠。

**一拨外国团能把「给服务员看」顶上去，第二天看着就像「掉下来了」。**
2026-11-06 午市 43 个会话里有 13 个德国人，其中 6 个在 14:34–14:41 七分钟内先后
点了「给服务员看」，那一场冲到 23%；后面四场都在 8–13%，看着像一路下滑。
按语言拆开就没有下滑了：西语客人一直是 5–11%，一次没动过。
`dash.js` 里 `_r_staff_mix` 这条结论专门盯这个——拿基线期各语言自己的使用率套到今天的
语言构成上，算出预期会话数，和实际差在 2×√预期 以内就判定「是客群变了，不是按钮出了问题」。
样本这么小的时候**不要按百分点卡阈值**：5 个会话和 9 个会话差 6 个百分点，但那就是噪声。

**页面上新开一个「加进清单」的入口，一定要把它的容器 id 加进 `SRC`。**
上线当天就踩了一次：`addonBlock()`（结算前加点）渲染在 `#order` 里，
第一版的 `SRC` 没列这个容器，那一整块的加点全落成了空来源。


- **收集口是公开的，挡不住有人拿 curl 直接灌数据。** Worker 会校验来源头（挡住别的网站的浏览器）、字段白名单和大小上限，但公开端点没有真正的办法杜绝伪造。小店的菜单，这个风险可以接受；真被灌了，数据能按时间段删掉重来。
- **只看得见扫码的人。** 没扫码、直接问服务员的客人完全不在数据里，而且扫码的人本身偏年轻、偏外国人。拿这份数据下「哪道菜最受欢迎」的结论，只对扫码客群成立。
- **样本小。** 一天几十桌，单项指标一周可能只有十几个数据点，别过度解读。
